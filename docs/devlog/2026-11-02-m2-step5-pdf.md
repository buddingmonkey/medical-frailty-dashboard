Start 07:14 CST, end 07:50 CST (`date`).

## Goal
Read the four seed states' PDFs into tables in the browser: pdf.js in the parser worker, rows
rebuilt from text positions, wrapped text and repeated headers handled, fixtures for GA, LA,
MT and NE.

## What happened
1. `pdfjs-dist` 6.5.438 was a day old, so pinned 6.4.299. Its standard build fails in Node 26
   (`Math.sumPrecise` missing) and may in older browsers: the legacy build everywhere. Its
   optional native canvas module is never installed. `isEvalSupported` no longer exists: pdf.js
   6 has no eval path at all.
2. Measured before writing rules: dumped every text run (x, y, width, font) of all five PDFs
   (GA A and B, LA, MT, NE: 721 pages). The docs' rule "a line with no code continues the row
   above" was true only for LA. GA, MT and NE wrap upward (Excel bottom-aligns), MT mixes both
   within one file, LA centers its headers, GA's columns move from page to page.
3. Built `pdf-layout.ts` test first (synthetic pages per quirk), then ran it on the full files
   after every change and compared with `pdftotext`. Each defect found became a test: runs
   joined across a 1 pt column gap (MT `L89.500-L89`), data lines taken for headers
   ("ICD-10-CM"), LA's printer writing two cells as one run, LA descriptions overflowing under
   the code column, NE's stray comma (`E09.349,`), MT's mixed alignment, GA-B's row with no
   code.
4. Rows: a dynamic program over the gaps between code lines picks the most row-like split
   (no value twice, no missing column, no lower-case start); the wrap direction only breaks
   ties, and the admin can force it on the page ("Wrapped lines").
5. Fixtures: the PDF excerpts were 0.5–6 MB (shared fonts, NE's scanned images), so the repo
   keeps only the text runs of 25 real pages (180 KB of JSON) plus the script that writes them.
   A tiny PDF writer (`fixtures/make-pdf.ts`) tests the pdf.js side.
6. Hands-on in `pnpm dev` found what jsdom could not: the page showed nothing. pdf.js's worker
   module, loaded inside our worker, took over its messages; and pdf.js cannot start its own
   worker from a worker (it reads `window.location`). Now our worker starts pdf.js's worker and
   hands it over as a port. Added an `admin` e2e project (second local Worker with the
   development bypass and its own migrated D1) so a real browser reads a PDF in CI.
7. Vite's worker format changed to ES modules: the parser worker is 159 KB, pdf.js (1.7 MB)
   loads only for a PDF. LA's 73 pages read in 0.8 s in Chromium. axe clean, light and dark.
8. Small fix seen in the screenshot: a blank designation showed as an empty item in "No
   qualification chosen for: , 0, 1, 2"; now "(blank)".

## Decisions
| Decision | Why | Who decided |
| --- | --- | --- |
| pdf.js legacy build | Node 26 and older browsers lack APIs the standard build uses | AI |
| Per-gap row splits instead of one wrap direction | MT mixes top- and bottom-aligned rows in one file | AI |
| Column edges from data, not headers | LA centers headers; GA's columns move per page | AI |
| Commit text-run snapshots, not PDF excerpts | 180 KB instead of ~9 MB; same layout data | AI |
| Admin e2e project on :8789 | The real worker path can only be tested in a browser; later M2 steps need admin e2e too | AI |

## Corrections and surprises
- The plan's wrap rule held for one state of four.

  Worker, so the tests took the direct path).

  656); `docs/sources.md` now says so.

  until page 1 (with the header) was added to the snapshot.
