# 2026-11-01: M0 step 5, site gate and Access JWT

**Session:** 2026-11-01 16:56–17:05 CST  •  **Milestone:** M0 step 5  •  **People:** project lead  •
**AI:** Claude Code, Opus main session, no subagents

## Goal

Add the two security middlewares: `access-jwt` (verify Cloudflare Access tokens in the Worker)
and `site-gate` (the whole site private until launch), with the required tests from
`docs/testing.md`.

## What happened

1. The project lead merged PR #4 and asked to continue.
2. The AI read the auth and gate sections, checked Cloudflare's guidance on validating Access
   JWTs, and asked three questions. The project lead chose:
   - **Who passes the gate:** anyone Access lets in.
   - **First admin route:** add `GET /api/admin/whoami`.
   - **robots.txt:** "make a good robots.txt so we start right".
3. Tests first: the AI wrote 30 failing auth, gate, robots and dev-bypass tests, plus the
   `whoami` schema test, with a fixture that generates its own RSA keys and signs good and bad
   tokens. Then it wrote the code: `verifyAccess` (jose), `siteGate`, `requireAdmin`, the
   robots route, `whoami`, and a `createApp({ getJwks })` factory, so tests use local keys and
   production uses Cloudflare's certs.
4. Two tests failed after the first pass. One was a bug in the test helper (a "service token"
   that secretly carried the admin email). The other was a real design gap: the local dev
   identity was not an admin.
5. With all tests green, the AI checked the running dev server with curl. The gate, dev bypass
   and spoofed `Host` header all behaved, but static pages had no `X-Robots-Tag`. Two new tests
   reproduced it, and the fix moved the header onto the final response.
6. `pnpm check:full` passes: 5 unit, 6 component, 39 API, 5 E2E tests.

## Corrections and surprises

- **Green tests, real bug.** All 37 tests passed, yet static pages lacked `noindex`. Responses
  built outside Hono (the static assets) do not pick up headers set with `c.header()` before
  the handler runs. Only the manual curl check found it.
- **A test helper lied.** `email: undefined` fell back to the default admin email, so the
  "service token" test was really an admin token. Changed the fixture to use `null` for "no email".
- **Process cleanup, done right this time:** the dev server was stopped by its process group.
  The first attempt used the wrong group ID (pnpm starts its own child group), and port 8787
  stayed busy until the AI looked up the real group with `ss -ltnp`.

## What a non-technical builder should take from this

1. Passing tests show that what you tested works, nothing more. After the tests pass, have the
   AI try the real running site.
2. Security settings should "fail closed": if something is missing or mistyped, the site
   should lock, not open.

## Follow-up: SEO and GEO (same session, before merging; ended 17:27 CST, start not recorded)

The project lead answered the AI-crawler question: **"I want best SEO and GEO practices. We
want AI to crawl to get the right info."** The AI pointed out that most AI crawlers do not run
JavaScript, so a Vue single-page app would look empty to them, and proposed that the Worker
render real HTML for public pages. The project lead approved that, chose `ai-train=yes` (the AI
had suggested leaving it out until the legal team reviews CPT text), and said a domain will
be bought in M7 or the site given to an organization to host.

Changes: `Content-Signal: search=yes, ai-input=yes, ai-train=yes` in the public `robots.txt`
(test first), a new `docs/seo.md`, a `CLAUDE.md` docs-table row, SEO/GEO items in roadmap M1, M3,
M4, M5, step 7 and M7, Cloudflare bot settings in "Going live", and `ai-train` added to the legal
team's review list in `docs/status.md`.

Lesson: an SEO goal turned into an architecture requirement (server-rendered HTML). Raising it
before M3 is cheap. After M3–M5 were built client-only, it would have meant rework.
